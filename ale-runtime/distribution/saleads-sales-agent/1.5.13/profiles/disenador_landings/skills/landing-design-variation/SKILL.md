# Landing design variation

Use this adjunct with `landing-coder`, inside its existing structure → art direction → build → review process. It adapts the owner's `landing-saleads.zip` design method to the business in the task. It does not replace the existing phase references, platform contract, source credits or canonical communication bet.

The source archive was written to promote the SaleADS SaaS brand. Its orb, logo, chat replicas, agent roster, prices, plan names and example results are **not customer assets or facts**. Use the delegated business's approved brand, photos, offer, evidence, locale and action. Even for a SaleADS-owned campaign, verify current claims from its approved brief; the archive is design material, not a live product specification. See `ADAPTATION.md` and `source-provenance.json` for the source map.

Managed instructions and design notes are English. Headlines, page copy, image alternatives, CTA labels, accessible names and the owner's delivery follow the trusted SaleADS task locale. Preserve an authentic source quotation in its original language only when its use is approved; do not turn source examples into quotations.

## Establish the direction before coding

1. Read the brief, current files/version, brand assets and any **same-business** prior design directions supplied by Ale. Separate fixed facts and promise from visual freedom. Missing photos or proof reduce viable directions; they do not authorize fabricated assets.
2. Read `references/narrative-and-copy.md`. Write one narrative sentence linking the visitor's need, the canonical promise, the evidence and the action. Consider the relevant narrative routes, then write eight distinct headline candidates in the page locale. Select a specific, supported headline; do not introduce a new promise to make it catchy.
3. Read `references/variation-axes.md` and record one compatible choice for each of its 13 axes in a task-workspace `design-direction.md`. Compare plausible directions before settling; do not let the familiar centered hero/three cards decide by habit. An already reviewed variation proposal from Ale may supply the choices. This adaptation does not run the archive's randomizer or claim a random draw.
4. Record the concept, selected headline, chapter sequence, 13 choices with their reasons, real-photo map, mobile composition, signature moment, comparison with prior same-business directions, and unavailable evidence. Reflect the chosen direction in the existing `design.json` fields; keep the extra design worksheet outside the server's closed metadata schema.
5. Freeze that worksheet for this design/revision. Feedback changes the requested part; preserve the rest. Revisit an axis only when the feedback, a real incompatibility or new approved evidence requires it, recording why. Do not draw a new direction each turn. A separate concept/alternative gets its own task artifact and remains attributable to the same business.

Prior design history is scoped input/output, not a shared global memory file. Keep the worksheet with this task's artifacts so Ale can carry it into a later same-business brief. If history is unavailable, say comparison is unavailable; do not claim uniqueness or create another learning service. Individual learning/curation remains the existing MCL responsibility.

## Build the idea, not a repeated template

Continue reading the existing `landing-coder` phase references. Build the mobile and desktop first screen, then the signature moment, evidence chapters and close. The close should resolve the same idea as the opening. Different composition is useful only when the product, message and action stay clear.

Read `references/platform-and-motion.md` before implementing effects or interactions. Use the existing approved font/icon catalogs, exact photo URLs and SaleADS HTML/CSS/declarative motion contract. Do not copy the archive's base HTML, scripts, chat controls, external CDNs or assumed registration paths. Distinguish a real configured action from an explanatory illustration; no inert action masquerades as a working button.

## Inspect the actual result

Read `references/visual-review.md`. Through Ale, obtain actual SaleADS validation and preview/captures for the saved artifact. Inspect first screen and full page at desktop/mobile, then detail crops where a full-page image is too small. Compare with the exact previous revision and same-business alternatives when available.

Keep the existing two consultative review rounds, `review.json` criteria and evidence format. The adjunct's questions sharpen those criteria; they do not add an incompatible server schema, turn an aesthetic score into approval, or prove conversion. Record missing visual coverage honestly. Return the files, worksheet and actual review evidence to Ale for governed CLI admission. Saving a proposed revision does not publish it; the owner's currently published version remains until explicit web approval of another exact version.
